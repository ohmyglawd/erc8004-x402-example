## 目標
做一個可操作的教學導覽 dApp，讓團隊可以「實際跑完一輪」並理解：
- **x402**（HTTP 402 Payment Required 的鏈下支付協議）在鏈上需要什麼：*可驗證的付款行為與事件*。
- **ERC-8004**（Trustless Agents，DRAFT）如何用三個 registry（Identity / Reputation / Validation）支援 agent 的發現、信任、驗證。

> 備註：此專案以教學/示範為主，並非 production hardened。

---

## Demo Story（用戶旅程 / 你可以做什麼）
這個 dApp 可讓你用三個角色操作同一套合約：

### 角色 1：Agent owner（服務提供者 / 擁有者）
你可以：
- **創建 agent（mint NFT）**：在 Identity Registry 註冊，鑄造 ERC-721（得到 `agentId`）
- **設定 agent URI**：更新 agent 的註冊檔/介紹檔指標（ipfs/https/data URI）
- **設定收款地址 agentWallet（EIP-712 兩步驟）**
  - 第 1 步：用 `newWallet` 帳號簽名 typed data（證明控制權）
  - 第 2 步：切回 agent owner 送出 `setAgentWallet`
- **發起驗證請求（validationRequest）**：指定 validator 幫你驗證某次交付/工作

### 角色 2：Service user（服務使用者 / 買家）
你可以：
- **領取測試 mUSDC**（MockERC20 mint）
- **授權 Paywall**（approve）
- **支付 mUSDC 使用服務**（payForEndpoint）
  - 這一步模擬 x402 的「付款後重試」概念：鏈上側重產生可驗證付款事件 `X402Payment`
- **留下評價**（Reputation Registry giveFeedback）
- **查看評價歷史**（直接抓鏈上事件 logs 顯示 NewFeedback / FeedbackRevoked）

### 角色 3：Agent Validator（驗證者）
你可以：
- 看到「指派給你」的驗證請求 requestHash 清單
- 針對某個 requestHash 回覆 `validationResponse`
  - `response`（0~100）可做通過/不通過或信心分數
  - `responseURI/responseHash/tag` 可放鏈下證據、審核報告、TEE/zk 等證明指標

## 合約組成（Base Sepolia）
- ERC8004IdentityRegistry（ERC-721 + URIStorage）
- ERC8004ReputationRegistry（評價訊號）
- ERC8004ValidationRegistry（第三方驗證 request/response）
- X402Paywall（最小化 on-chain 支付目標：ERC20 transferFrom + X402Payment event）
- MockUSDC（MockERC20）

Base Sepolia addresses：repo 內 `deployments/base-sepolia.json`

## 技術重點（給工程團隊）
- **x402 是 HTTP 協議**：此 demo 聚焦在「鏈上支付事件」與「off-chain 服務可驗證付款」的接合點。
- **評價歷史**：完整細節（endpoint/feedbackURI/hash）在此範例主要透過 *events* 取得，符合 ERC-8004 的設計方向（便於 indexer/subgraph）。
- **RPC 可靠性**：Base Sepolia 公共 RPC 偶有 503，本 dApp 加了多個公開 RPC fallback。

## 下一步（如果要更完整支援 x402 協議）
後端通常需要：
- 在受保護 API 實作 402 + PAYMENT-REQUIRED header
- 驗證客戶端付款 payload / facilitator
- 設計 refId 生成規則（HTTP 請求 ↔ 鏈上付款事件關聯）
- 防重放（同一筆付款不可重複兌換）
- pricing / quota / rate limit / observability / 對帳
